# 第一章：从一次真实任务走通 v1.2.24

本章只研究 `c6262f9d4002d86a1f1795c306aa329d45361d12`，也就是 `release: v1.2.24`。所有源码块都出自这个提交。先把这一版作为完整系统学懂，后面再讨论另一版怎样修改它。这里的 `MessageV2` 是这一版自己的消息格式名称， **不是后来重写的 Session V2 架构** ；不要因文件名相似而把两者接成同一条执行链。

贯穿全章的任务是：“读取登录实现，让 explore 找出真正的登录入口，运行相关测试，最后总结。”假设项目里有 `src/auth/login.ts` 和 `test/auth.test.ts`。这些项目路径、测试输出与下文短 ID 都是解释用的例子，并未实际执行模型或测试。真正运行时 ID 带有由 `Identifier` 生成的后缀；为了画出所有权关系，本文用 `ses_parent`、`msg_u1`、`msg_a1`、`call_read1` 代称。

学完后，应能不看界面就回答：用户那句话存在哪里，谁调用模型，谁调用工具，父会话何时等待子会话，取消信号怎样到达测试进程，以及重开程序时什么还存在。理解这些问题，比背下每个目录名更接近理解一个 coding agent。

## 一、先区分配置身份、会话记录和活动执行

把“agent 在跑”拆成三句话，源码会容易许多。`Agent.Info` 描述以什么身份工作；`Session.Info` 描述这段对话属于谁、在哪个项目；`SessionPrompt.loop` 描述本次正在推进这段对话的活动函数。三者可以相关，但不是同一个对象，也不具有同样的生命周期。

`Instance.state` 负责按当前项目实例缓存这些定义。实例还提供 `directory`、`worktree`、`project` 等运行背景。它解决“我正在为哪个项目工作”的上下文问题，并没有给每个 Session 分配一套隔离文件系统。父会话和 child Session 通常仍在同一项目目录操作；它们的历史不同，不代表文件副作用隔离。

在我们的例子里，主会话使用 build。模型决定委派查找任务后，task 会选 explore；主 agent 没有变成 explore，父会话也没有改名。系统只是多了一段以 explore 身份推进的子会话历史。

## 二、Session、message、part：把“聊天内容”拆成三层

Session 是长期容器，保存项目、工作目录、标题、parentID、权限等元信息。它不保存一个永远运行的循环。创建 Session 时，`Session.create` 取得 `Instance.directory`，再交给 `createNext` 生成身份和记录；这一阶段可以完全不请求模型。

message 是会话中的一次用户输入或一次 assistant 输出。user message 除了 role、时间，还记录 agent、model、可选 system 和输出格式；assistant message 记录 parentID、模型、usage、finish、error 等。part 则承载消息中的具体成分：text、reasoning、file、tool、step-start、step-finish、patch、compaction 等。一个 assistant message 绝不是一个纯文本字符串。

| 本例对象 | 所属与内容 | 为什么单独存在 |
| --- | --- | --- |
| `ses_parent` | 登录分析这段会话 | 可以跨多次用户提问保留历史 |
| `msg_u1` | 属于父 Session 的原始任务 | 固定本次请求的 agent/model 等选择 |
| `msg_a1` | `parentID = msg_u1` 的第一轮 assistant | 保存本轮模型和 finish/usage |
| `prt_read1` | 属于 `msg_a1`，`callID = call_read1` | 记录 read 的状态、输入与结果 |
| `ses_child` | `parentID = ses_parent` 的探索会话 | 子任务有独立对话历史 |

两个 parentID 容易混淆： **Session 的 parentID 指父会话；assistant message 的 parentID 指它回答的用户消息。** 一个是会话树，一个是对话中回应的归属。另一个常见错误是把 part ID 与 callID 当成同一个值。part ID 是本地持久记录身份，callID 是模型工具调用的关联键，SDK 的结果事件要靠它找回对应 part。

工具 part 的 `state` 是判别联合：`pending → running → completed`，或在失败时进入 `error`。pending 可以表示模型刚开始输出工具输入；running 有完整输入和开始时间；completed 保存输出、metadata、附件、结束时间；error 保存错误文本。界面显示“正在运行测试”与下一轮模型读到“测试成功”，来自不同状态中的同一条工具记录。

## 三、数据库保存事实，Bus 通知当前观察者

先看保存 message 的最小实现，后面每次出现 `Session.updateMessage` 都应能想到它究竟做了什么。

<!-- EXCERPT c6262f9d4002d86a1f1795c306aa329d45361d12 packages/opencode/src/session/index.ts 679 699 -->
**真实源码 · A · v1.2.24** — [`packages/opencode/src/session/index.ts`，L679–L699](https://github.com/gaoch023/opencode/blob/c6262f9d4002d86a1f1795c306aa329d45361d12/packages/opencode/src/session/index.ts#L679-L699)

```typescript
  export const updateMessage = fn(MessageV2.Info, async (msg) => {
    const time_created = msg.time.created
    const { id, sessionID, ...data } = msg
    Database.use((db) => {
      db.insert(MessageTable)
        .values({
          id,
          session_id: sessionID,
          time_created,
          data,
        })
        .onConflictDoUpdate({ target: MessageTable.id, set: { data } })
        .run()
      Database.effect(() =>
        Bus.publish(MessageV2.Event.Updated, {
          info: msg,
        }),
      )
    })
    return msg
  })
```

输入 `msg` 被拆成主键、session_id 和其余 JSON 数据。`onConflictDoUpdate` 意味着这不只是“插入一条新消息”：同一个 assistant 在获得 finish、usage、error 后，可以用同一 ID 更新记录。函数返回保存的消息对象；它既不调用模型，也不等待用户下一次操作。

`Database.effect` 把更新通知安排在数据库操作对应的 effect 阶段；如果处在显式事务中，effects 会等事务完成后再触发。因此读者应把顺序理解为保存数据，再安排发布 `message.updated`。但不要再多推一步，认为数据库和网络观察者共享一个分布式事务：Bus 订阅者、SSE 客户端和数据库不是一个原子提交系统。

`Session.updatePart` 对 part 做同样的 upsert，并发布 `message.part.updated`。数据库的 `session`、`message`、`part` 表通过主键与外键关联；删除会话时 message/part 有级联清理，child Session 的删除则由会话服务另外递归处理。使用 SQLite 不等于只有内存聊天，也不等于所有活跃执行状态都在 SQLite。

Bus 的订阅表是 `Instance.state` 里的 Map。`Bus.publish` 找到特定事件和通配订阅者，并通过 GlobalBus 提供带 directory 的通知。它适合让界面或服务端连接看到“刚刚变了什么”，不是一个任意历史游标都能重放的事件日志。程序重启后可以重新查询 message/part，但之前 Promise、AbortController 和 Bus 订阅关系不会从这些表自动复活。

流式文本还有一个微妙边界：processor 在内存中累加 text，再发布 `PartDelta`；`Session.updatePartDelta` 只发增量通知，不把每个 delta 都写入 SQLite。到 text-end 时完整 part 才再次保存。由此能解释：界面曾看到一段未完成输出，不证明进程崩溃后数据库一定包含那段输出的每个字符。

## 四、prompt 的入口先存用户消息，再决定是否回复

假设父 Session 已创建，调用者把四步任务作为 text part 传给 `SessionPrompt.prompt`。这里的“接收输入”还没有后来 inbox 那样单独的待处理身份；它直接走用户消息与 parts 的保存路径。

```typescript
  export const prompt = fn(PromptInput, async (input) => {
    const session = await Session.get(input.sessionID)
    await SessionRevert.cleanup(session)

    const message = await createUserMessage(input)
    await Session.touch(input.sessionID)

    // this is backwards compatibility for allowing `tools` to be specified when
    // prompting
    const permissions: PermissionNext.Ruleset = []
    for (const [tool, enabled] of Object.entries(input.tools ?? {})) {
      permissions.push({
        permission: tool,
        action: enabled ? "allow" : "deny",
        pattern: "*",
      })
    }
    if (permissions.length > 0) {
      session.permission = permissions
      await Session.setPermission({ sessionID: session.id, permission: permissions })
    }

    if (input.noReply === true) {
      return message
    }

    return loop({ sessionID: input.sessionID })
```

先 `Session.get` 确认会话，再清理 revert 状态，接着 await `createUserMessage`。这个 await 结束时，函数已经选好 agent/model、处理输入 parts、触发 `chat.message` 插件、保存 message，再逐个保存 parts。随后 touch 更新会话时间。这些步骤不会因为模型尚未输出而暂时藏在一个 admission queue 中。

`tools` 是兼容字段：输入中的布尔开关被翻译成权限规则，必要时保存到 Session。它不是工具执行的结果，也不等于给工具传入业务参数。`noReply` 的含义则很直接：消息保存后返回，不启动这次回复循环。因此“prompt 调用成功”和“已经调用模型”是两个应分开观察的事实。

`createUserMessage` 对 agent 的选择顺序是输入明确指定，否则 defaultAgent；model 则优先输入，再 agent 配置，再最近用户消息的 model，最后才默认 provider model。这个顺序让多轮对话延续选择，而不是每条输入都悄悄重置模型。

如果用户输入中有 `@explore` 形成的 agent part，入口会增加 synthetic text，提示模型生成合适任务并调用 task；这和代码直接切换当前循环的 agent 不是同一回事。文件引用也会被展开成适合模型的上下文或附件，不能认为 input.parts 会无条件原样变成 HTTP 请求中的字符串数组。

本例保存后可画出：`ses_parent → msg_u1 → prt_u1(text)`。此时没有 `msg_a1`，没有任何测试进程，甚至 `noReply=true` 时可以永远没有本轮模型调用。这个检查点适合第一次下断点：确认数据进入系统与开始执行确实是分开的两步。

## 五、同一 Session 的第二个调用者不会自动创建第二条 loop

会话可以同时被多处引用，但同一项目实例内的执行状态另由 `SessionPrompt.state` 管理。每个活动 sessionID 对应一个 AbortController 和 callbacks 列表。

```typescript
  export const loop = fn(LoopInput, async (input) => {
    const { sessionID, resume_existing } = input

    const abort = resume_existing ? resume(sessionID) : start(sessionID)
    if (!abort) {
      return new Promise<MessageV2.WithParts>((resolve, reject) => {
        const callbacks = state()[sessionID].callbacks
        callbacks.push({ resolve, reject })
      })
    }

    using _ = defer(() => cancel(sessionID))

    // Structured output state
    // Note: On session resumption, state is reset but outputFormat is preserved
    // on the user message and will be retrieved from lastUser below
    let structuredOutput: unknown | undefined

    let step = 0
    const session = await Session.get(sessionID)
    while (true) {
      SessionStatus.set(sessionID, { type: "busy" })
      log.info("loop", { step, sessionID })
      if (abort.aborted) break
      let msgs = await MessageV2.filterCompacted(MessageV2.stream(sessionID))
```

`start` 发现该 Session 已有活动控制器时返回空值；`loop` 因而不再进入第二个 while，而是创建 Promise，把 resolve/reject 保存到 callbacks。原先的 loop 是活动推进者，后来进入的调用者是等候者。`resume_existing` 则尝试使用已有 signal，不能把它理解为创建新的进程。

`resume_existing` 在本版还有一个具体用途：[直接 shell 的收尾路径](https://github.com/gaoch023/opencode/blob/c6262f9d4002d86a1f1795c306aa329d45361d12/packages/opencode/src/session/prompt.ts#L1481-L1490)。`SessionPrompt.shell` 先占用同一套活动状态；如果执行期间有新 prompt 保存消息并加入 callbacks，shell 结束后不会立即 cancel，而是用 `resume_existing: true` 复用原 signal 启动 loop，处理已经保存的输入；没有 callbacks 才按默认路径 cancel。这里的直接 shell 与模型调用 BashTool 是不同入口。它是后来 B 中 `ShellThenRun` 显式状态的手工前身：先完成 shell，再推进等待中的模型工作，而不是同时再起一个会话循环。

我们的任务执行到 read 时，用户又补一句“只运行登录相关测试”。入口仍会先保存新的 user message，之后才来到 loop；如果已有 owner，它等待原循环最终返回。原循环下一次读取消息历史时有机会看到补充，所以信息不是通过 callbacks 参数传给模型的。callbacks 解决“哪个调用者等最终答复”，数据库消息解决“模型以后会看到什么”。

`using ... defer` 保证作用域离开时调用 cancel，释放内存活动状态。while 顶部设置 busy，检查 abort，再读取压缩后的历史。不要因为这里检查了 signal 就把取消看成强制回滚：如果上一工具已经写了文件，abort 不能把文件自动恢复；它只能要求相关活动停止，并依赖工具遵守协作取消协议。

这一版状态表是实例内存结构，不是跨机器锁。同一进程中对同一实例的防重入，不能推出两个独立服务进程也能串行推进同一数据库 Session。这个范围限制是未来学习 coordinator 和分布式所有权时必须保留的参照。

## 六、loop 从历史判断“接下来做什么”

每轮读完历史，loop 倒着寻找 lastUser、lastAssistant、lastFinished，并收集尚待处理的 compaction/subtask parts。这里不是对着一个永久驻留的“智能体对象”发 next，而是根据保存的对话状态重建下一步判断。

```typescript
      let lastUser: MessageV2.User | undefined
      let lastAssistant: MessageV2.Assistant | undefined
      let lastFinished: MessageV2.Assistant | undefined
      let tasks: (MessageV2.CompactionPart | MessageV2.SubtaskPart)[] = []
      for (let i = msgs.length - 1; i >= 0; i--) {
        const msg = msgs[i]
        if (!lastUser && msg.info.role === "user") lastUser = msg.info as MessageV2.User
        if (!lastAssistant && msg.info.role === "assistant") lastAssistant = msg.info as MessageV2.Assistant
        if (!lastFinished && msg.info.role === "assistant" && msg.info.finish)
          lastFinished = msg.info as MessageV2.Assistant
        if (lastUser && lastFinished) break
        const task = msg.parts.filter((part) => part.type === "compaction" || part.type === "subtask")
        if (task && !lastFinished) {
          tasks.push(...task)
        }
      }

      if (!lastUser) throw new Error("No user message found in stream. This should never happen.")
      if (
        lastAssistant?.finish &&
        !["tool-calls", "unknown"].includes(lastAssistant.finish) &&
        lastUser.id < lastAssistant.id
      ) {
        log.info("exiting loop", { sessionID })
        break
      }
```

`lastUser` 代表最近输入，`lastAssistant` 代表最新模型消息；`lastFinished` 指有 finish 标记的 assistant。退出条件要求最新 assistant 已有 finish，finish 既不是 tool-calls 也不是 unknown，并且用户消息 ID 排在 assistant 之前。这个条件依赖这一版 ID 的顺序性质；它不是后来基于 durable event sequence 的队列推进协议。

例如 `msg_a1.finish = tool-calls`，即使 read 已完成也不会把整个任务当成最终答复，因为模型还需要看到 read 结果。相反，`msg_a4.finish = stop` 且没有更新的 user message 时，下一次循环开头会退出。源码因此有一个看似奇怪的行为：processor 可能返回 continue，但外层下一轮刚开始就发现模型已正常完成并 break；两层返回值各自回答的问题不同。

退出检查之后，loop 先处理显式 subtask，再处理 compaction task，必要时根据上一轮 usage 安排自动压缩，然后才进入普通模型分支。普通分支选择 agent，创建 assistant message 与 processor，准备 tools，收集环境和项目 instructions，转换模型历史。标题和 summary 辅助任务并非全部在主路径上等待完成；不要以为每个内部 LLM 请求都代表用户任务多走了一步。

`step` 是这次 loop 中的步数计数。到 `agent.steps` 时，这一版会向模型加入 MAX_STEPS 提示，而仍可提供工具；所以它主要是提示层限制，不能当作运行时绝对禁止第 N 次之后工具调用的硬栅栏。模型回报的 token usage 也不是 step，两者分别描述资源消费和业务轮次。

## 七、一次模型调用如何接上工具

## 九、模型续轮不是 SDK 黑盒自动完成的整个任务

read 的结果保存后，processor 把本次处理结果交回 loop。外层重新构造模型历史，`MessageV2.toModelMessages` 将本地 message/part 降低为 provider 可接受的 user/assistant/tool 表达；不是把数据库行 JSON 原样发送。它还处理附件、已压缩输出和不同 provider 对工具结果的格式差别。

模型下一轮据此决定调用 task；再下一轮看到 task 的摘要，调用 bash；最后看到测试输出，生成总结。这个多轮决策由 OpenCode 外层 loop 推进，AI SDK 承担一次流请求与它暴露的工具回调，而不是另有一个隐藏的无限 agent loop 替代了 `SessionPrompt.loop`。

这里先检查 auto 配置，再计算 token 总量和预留容量。阈值依赖模型的 context/input/output 限制，不是固定“对话超过若干条就删”。返回 true 只代表需要压缩；loop 随后创建 compaction part，再由专用分支推进摘要。因此压缩是主循环可理解的一类任务，不是底层数据库自动清理。

`SessionCompaction.process` 选择隐藏 compaction agent，创建 summary assistant，使用不带业务工具的模型请求生成延续摘要。它可以调用插件调整压缩提示；完成后视情况重放用户输入或添加 synthetic user 继续指令。`MessageV2.filterCompacted` 在后续组装历史时保留需要的摘要边界。压缩不是把原聊天全部物理删除，更不是把刚执行的测试重新跑一遍。

另有 prune 专门标记旧工具结果的 compacted 时间，控制已经很久远的大段输出进入上下文。prune 与 summary compaction 分属不同处理：前者主要减掉旧工具输出的负担，后者生成整个工作状态的摘要。模型看到摘要可以继续推理，但并不等于拥有旧文件附件或所有原始输出的全部细节。

网络故障的“继续”又是另一件事。processor 捕获 provider 错误，把上下文溢出导向 compact；可重试 API 错误则延迟重试。

最后，重新打开程序不是上述任意一种 continue。SQLite 中的 Session/message/part 可重新读取；运行中的 provider stream、Promise 回调、AbortController、Bus 订阅、shell 进程句柄都是另外的资源。本版没有根据一条数据库 running 状态自动恢复同一个 OS 进程的能力。能看到历史，不等于程序已经证明可以安全接续未知的模型请求和工具副作用。

## 十三、把整个例子再走一遍

现在无需依赖界面，也可以在纸上模拟这段任务。创建 ses_parent 时仅插入会话元信息；prompt 把任务写成 msg_u1/parts；loop 获得内存活动权，第一次读历史后建立 msg_a1，准备 build、system、read/task/bash 描述。LLM.stream 调 SDK，模型输出 read 调用，SDK 执行回调，processor 将 prt_read1 从 pending 推到 completed。

下一轮历史里有登录实现内容，于是模型创建 explore task。TaskTool 创建 ses_child，child 用户输入只有明确委派的查找问题；child loop 在相同项目资源上以 explore 的配置查文件。父 task Promise 等待，但其他 Session 和事件回调仍可工作。child 总结入口后，其最后 text 被包装成父会话的 task output。

第三轮父模型读到入口及测试建议，bash 获批后创建 shell/test 进程。输出不断进入运行 metadata；exit=0 后工具 completed。第四轮模型才有依据总结“入口在哪里、测试运行了什么、结果是什么”。如果第三轮被用户取消，shell 清理是额外动作，不能只改 SessionStatus 就假定测试已停止；如果只是进程重启，也不能把历史 running 视作进程还活着。

这条因果链中，Agent 是配置，Session 是记录，loop 是活动推进，provider turn 是一次模型流，tool 是宿主能力入口，task 带来 child Session，bash 带来 OS 进程。把这些名词分开以后，后来版本新增的调度器、事件流或后台 job 才有明确的落点，而不会变成另一堆需要死记的名称。

## 十四、深度自测：问题与推导答案

### 1. 用户补充测试范围时，为什么 callbacks 不用保存补充文本？

因为 prompt 先把补充保存为新 user message，再调用 loop。callbacks 保存的是等结果的调用者，不是模型输入。owner 下一轮重读历史才看到补充；若只向 callbacks 增加一段文本而不保存 message，正常历史转换不会因此把它发给模型。

### 2. 为什么一个 completed 的 bash part 仍可能代表测试失败？

completed 表示工具调用完成并返回标准结果。测试退出码一是命令业务失败，可能仍由工具正常返回；应结合 exit 与 output 判断。只有启动异常或执行抛错等才走工具错误路径。把工具调度成功与被调用程序成功混成一个布尔值，会让 agent 误报验证结果。

### 3. task 的 parentID 能证明子 agent 继承父会话全部上下文吗？

不能。parentID 建立会话关系，TaskTool 实际向 child 传的是 params.prompt 展开的 parts，而不是父 message 数组。父模型若希望子 agent 参考某条发现，应在委派 prompt 中写清。历史复用只有在 task_id 找到原 child 时才继续那段 child 自己的对话。

### 4. task 正在等待 child，是否说明整个应用不能处理别的请求？

不是。await 暂停这条异步调用链，等待 child 结果；它让出事件循环。其他会话、网络和输出回调仍能推进。同一 Session 不再启动第二个 owner 是状态表的业务约束，不是 JavaScript 只能运行一个 Promise 的限制。

### 5. detached=true 为什么没有让 bash 变成“后台工具”？

因为 spawn 的进程组设置和 execute 的返回协议属于两层。detached 有助于 Unix 组信号管理，但这段 execute 后面仍 await exit/error。真正让父模型先拿 job ID 继续，需要额外的返回、查询、完成通知和取消协议，本版这段 bash 没有提供那套机制。

### 6. 把 message.updated 通知发给客户端，为什么不能称作完整事件溯源？

因为本版权威记录主要是可更新的 message/part 行，Bus 订阅是内存通知。没有一条独立、不可变且带持久游标的完整事件日志保证离线后逐条重放；delta 甚至可能尚未落盘。重新查当前快照和重放每个历史事件，是不同恢复能力。

### 7. processor 返回 continue，为什么 loop 可能马上结束？

processor 回答本次流处理有没有被阻断、失败或要求压缩；外层还要根据完整历史判断是否需要新的 provider turn。普通 stop finish 可以先得到 continue，再在下轮顶部退出。把这两个条件合并理解，会找错多轮工具循环的真正控制位置。

### 8. agent.steps=3 能保证第四个工具绝不会运行吗？

不能如此保证。本版在达到步数时向模型加入 MAX_STEPS 提示，仍组装工具；step 还是 loop 迭代计数，不是全会话工具次数。想实现硬限制，必须在请求工具目录、执行分派或循环调度上施加相应约束，不能只依靠模型遵守文字提示。

### 9. 取消后能否直接删除 child Session 和工具记录来“恢复干净”？

这样会混淆停止活动与删除事实。child 可能已经发现代码或改过文件，bash 也可能产生不可撤销副作用；记录恰好是解释这些结果的依据。源码的 cancel 针对活动 signal，TaskTool 移除监听，不把删除历史作为取消的一部分。

### 10. 读懂本章后，学习下一版最应追问什么？

应追问这些具体责任是否换了所有者：同 Session 活动权由谁管理，用户消息何时可见，调用记录何时相对副作用落库，谁等工具完成，后台任务怎样回注结果，进程重启怎样处理未知状态。先找到这些责任的新实现，再看新的 Effect 或事件 API；这样是在迁移已经建立的因果模型，而不是从新目录重新背一遍名字。
