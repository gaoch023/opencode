你最关心的两条新链

父模型 → subagent(background=true)
  → 校验 agent / 权限 / 深度，创建或续用 child Session
  → child.prompt → SubagentJob.start → Session.resume
  → 父工具立即返回 running + sessionID
  → 子会话完成 → synthetic 完成/失败结果送入父会话
父模型 → shell(background=true)
  → Shell.create 启动真实 OS shell 进程，输出持续写文件
  → Job.start + background，持久化可恢复通知元数据
  → 父工具立即返回 running + shellID + 输出文件
  → 命令完成 → synthetic 输出/退出状态送入所属 Session

这已经超出 shell 命令里手写 &：它有 OpenCode 自己的执行身份、观察、前后台转换和通知协议。shell 还提供 HTTP list/create/get/output/remove 接口；应用 API 与模型直接可用的工具目录仍要分开理解。

仍要分清的边界

  • Agent 是策略身份；Session 是对话身份；子 agent 通常仍是宿主进程内的异步执行链，不是每个 child 都启动 OS 进程。
  • shell 命令会创建真实 OS 子进程；PTY 是带伪终端的交互进程。shellID、SessionID、Job ID 与 PID 不要混用。
  • 当前已有恢复机制，但不保证所有 OS 进程跨服务器重启存活，也不保证任意外部副作用 exactly-once。
  • 当前父会话取消与后台子任务的关系应看 07，不要直接沿用旧 V1 的递归后代取消规则。
  • 学习基线使用 Bun 1.3.10，N 使用 Bun 1.4.4。此前 Bun 1.3.14 的依赖安装结果不能视为新版本运行验证。

第三遍：理解 Agent 与 child Session

先看 agent/agent.ts:24。Agent.Info 包含 name/mode/model/prompt/permission/steps 等。build、plan、general、explore 是配置身份；调用 Agent.get('explore') 本身不会启动线程或模型。

然后看 tool/task.ts:45：

父 loop 的 task tool call
  → 校验能否使用指定 subagent
  → 查找 task_id，或 Session.create({ parentID: 父 Session })
  → 选择子 agent/model，配置其工具权限
  → 把父 abort 接到子会话 cancel
  → await SessionPrompt.prompt({ sessionID: 子 Session, ... })
  → 取最后文本，返回 task_id + task_result 给父 tool call

关键源码：创建子会话 :66、取消与子 prompt :119、结果包装 :145。

child Session 在同一个执行宿主中拥有另一段历史和一次独立 loop。它可以调用 bash 继而创建 OS 子进程，但“子 agent 的会话”与“bash 的子进程”是两回事。多个 task 工具若被并发调度，各自可以推进不同 Session；父工具逻辑 await 子任务，不等于它阻塞整个 JS 事件循环。

第四遍：持久记录与活跃执行分别在哪里

层 基线位置 保存什么
会话身份 session/session.sql.ts:11 project、parent、directory、title、permission 等
消息与内容块 session/session.sql.ts:42 message/part 的 JSON 内容与归属关系
数据写入与通知 session/index.ts:679 upsert message，再通过 Bus 通知消费者
正在执行的状态 session/prompt.ts:65 Instance 内的 Session → AbortController + 等待回调
UI 状态 session/status.ts busy/idle/retry 等对外状态

Session 数据写在 SQLite，活跃 loop 的 Promise、AbortController 和 callbacks 并没有因此变成可持久执行的任务。重启后能读回历史，不等于会自动知道某个命令究竟执行到了哪一步。这个区别是理解 V2 重构最重要的前置知识之一。

第五遍：异常、取消与压缩

  • processor.ts:353：区分上下文溢出、可重试错误、终止错误；retry 会经过退避和 abort-aware 等待，不应只看 provider SDK 的重试参数。
  • processor.ts:401：退出时将没结算的工具 part 标成错误，避免 UI 永远显示 running。
  • prompt.ts:528：处理待执行压缩；:704 根据 processor 结果触发后续压缩。
  • tool/bash.ts:172：真正启动 shell；:208 把 abort、timeout 与杀进程树接在一起。
  • prompt.ts:264：Session 取消通过 AbortController 发出协作信号。外部副作用已发生时，取消不会自动回滚文件或网络请求。

4. 模型选择与续接切换

subagent.ts:75-98 解析 model reference，确认 provider/model 在 available 集合，variant 也必须存在。

新建子会话的模型优先级（:184）为：显式 model → 子 agent 配置模型 → 父 Session 模型。

继续已有会话时（:168-181）：

  • agent 变更会调用 switchAgent。

5. 一条完整的执行链

父模型调用 subagent
  → 深度/agent/权限校验
  → 创建或验证直属 child Session
  → child prompt admission
  → SubagentJob.start(recovery)
      → Job.start(id=childID)
      → sessions.resume(childID)
      → 取最近 completed、无 error 的 assistant 文本
  ├─ 前台：jobs.block → completed 输出给本次工具调用
  └─ 后台：jobs.background + 注册 observer → running 立即返回
                                         → 完成后 synthetic 输入通知父会话
  • admission 在 job 之外（subagent.ts:203-218）：已有 running job 的 start 会 join/跳过自己的 run effect，但追加 prompt 仍能送达正在执行的 child。
  • 新建后台 child 的首次 prompt 使用 resume:false，再由 Job 所有的 resume 执行，见 :212。
  • :220-227 保存 kind=subagent、parentSessionID、childSessionID、agent、description 的恢复元数据并启动 job。
  • :229-231 是明确的立即返回路径；不是仅在 shell 里使用 &。
  • 前台也可被转后台：:234-243 的 jobs.block 返回 backgrounded 时解除等待并注册通知，不重新创建一个 child。

6. 取消与完成通知的作用域

前台等待被 interrupt 时，subagent.ts:234-239 同时执行 sessions.interrupt(childID) 和 jobs.cancel(childID)。失败或取消会保留子 Session ID 给模型，便于后续明确续接（:245-255）。

5. 重试、终止、取消：别混成一件事

  • 正常结束：模型没有需继续的本地工具且没有新输入；A/B 的 stop/unknown/tool-calls 历史条件与 C 的 needsContinuation 不是同一实现。
  • 工具报错：通常作为工具结果让模型读到，和 provider 失败不是同一个错误通道。用户拒绝权限/问题则可让 loop 停下；C 显式识别 DeclinedError/RejectedError 并中断（C runner/llm.ts:144,306）。
  • provider 可重试错误：A 会继续其内层 processor 重试；B 最多 5 retries；C 底层 RequestExecutor 有 2 次 HTTP 请求重试，但 Session runner 没有 V1 式全轮重试与 retry 状态策略。
  • 用户中断：停止运行中的执行链，清理工具和 assistant；不等于删除 Session 历史。
  • 进程崩溃：C 开始新 drain 时把历史残留 running/pending tools 标为 interrupted，不假装工具仍活着，也不静默重放 shell/文件写入。

9. V2 API 可用性与 runner 能力必须分开

10. 重试还有一层：HTTP 请求重试 ≠ Session turn 重试

4. V2 的重要新边界：接受输入 ≠ 执行输入

链条直接来自 B 源码：

SessionV2.prompt({id?, sessionID, prompt, delivery?, resume?})
 -> SessionInput.admit
 -> durable PromptAdmitted + session_input
 -> resume !== false 时 execution.wake(sessionID)
 -> 返回 admission receipt

SessionExecutionLocal（process-global）
 -> Coordinator(wake/run)
 -> SessionStore.get(sessionID)

  • B packages/core/src/session/input.ts:41：admit 如 ID 已存在先返回；否则发布 PromptAdmitted；冲突并发后再查既有记录。same ID 必须匹配 Session、编码后的 prompt、delivery（:191），否则 facade 抛 PromptConflictError。

  • B packages/core/src/session/projector.ts:348：Prompted projector 同事务调用 projectPrompted 标记 promoted_seq，再 run 消息投影。:362 PromptAdmitted 只建立 inbox 记录。

steer、queue、wake、resume 四个不同概念

  • steer：B input.ts :245，取到 captured cutoff 的所有 pending steers，按 admitted_seq 升序 promote。在 provider turn 完成后的安全边界才能生效，不抢断当前 token stream。
  • queue：B input.ts :268，只取最早一条 pending queue。当前 drain 的 continuation 结束之后才消耗；处理完这一条再判断 continuation/下一条。
  • wake：B run-coordinator.ts :81，运行中只设 pendingWake=true；不是每个请求都 fork 一轮模型调用。空闲启动 force=false。
  • resume：B run-coordinator.ts :67，已有 owner 则 join Deferred；空闲启动 force=true。显式选择“从持久历史继续”与“通知有输入”有不同风险语义。
  • B runner/llm.ts :396：wake 没有 pending 输入则返回；:402 外层循环只在 continuation 结束后取 queue；:409 continuation 内设置 promotion=steer；:195 推入新用户输入时重置 step allowance。

例子：模型刚发工具调用时用户提交 steer A、queue B。当前 provider turn 和已启动工具先结算；下一轮将 A 加入历史，B 继续留 inbox。直到工具续接/模型回答不再要求 continuation，才 promote B，重新进入下一段对话。

5. V2 运行协调是“本进程每会话一个 drain”，还不是分布式调度

  • B packages/core/src/session/execution/local.ts:16 创建 coordinator；:17 drain 时用 SessionStore 查最新 Location；:20 在 Location services 中调用 runner。
  • B 同文件 :40 明确 makeGlobalNode。SessionRunner 的实现 B runner/llm.ts :423 是 makeLocationNode。一个 Location runner service 可以执行多个不同 Session；不要每个 Session 都建一整份 service layer。
  • B packages/core/src/session/run-coordinator.ts:28 active 是进程内 Map。不同 Session key 可并发；相同 key 只有一个 owner。active 返回的是 Map keys 的快照（:103），不是 durable busy 标志，不是所有后台子任务列表。
  • 同文件 :51 settle 处理合并 wake 的后继执行；:94 interrupt 设置 stopping、清除当时已登记 pendingWake，再 Fiber.interrupt(owner)。中断等待清理完成；清理期间新来的 wake 仍能注册后继，因此“取消”不等于永久封禁这个会话。
  • resume 等待者自身被中断不应取消 owner：对应测试 B packages/core/test/session-run-coordinator.test.ts:351。这解决“断开一个 HTTP 等待者是否杀死整个会话”的所有权问题。
  • B runner/llm.ts :180 每轮检查 Session 的 directory/workspaceID 是否仍匹配 runner Location，不匹配 interrupt。但这不是完整 distributed lease/epoch fencing。

6. 取消、崩溃、恢复：不可把 durable 理解成“可安全重做一切”

V2 interrupt 只针对当前进程 active execution；空闲或缺失 Session 不做任何事情。durable inbox 不被删除，后续可 wake/resume。进程重启后 Coordinator 的 active Map 为空；当前 provider 是否已真正接受请求可能不可知。

B runner/llm.ts :119 的 failInterruptedTools 扫描历史中 pending/running tool，写入 Tool.Failed，错误文本 Tool execution interrupted，保留 provider metadata，并带 assistantMessageID 区分不同轮复用的 callID。它把不明确的历史执行收敛为失败；没有擅自重跑文件修改、shell 命令等副作用。

B runner/llm.ts :398 只有有 eligible input 或显式 force 才进入 runner；这能说明：wake 不会仅因历史中存在一个未续接的 assistant 就自动发请求。它不是完整 crash-recovery daemon。显式 resume 可以从投影历史继续，但用户/调用方承担继续的决策，而不是系统保证 provider exactly-once。

05 · 进程、后台任务与 PTY

历史快照说明（2026-10-22 更新）： 本文比较 v1.2.24 与 2026-10-08 的 388406238b，其中“当前/最新/V2”都指当时快照。远端已在 2026-10-10 推广 V2；当前 2.1.3 已支持 subagent 与 shell 后台执行、持久通知及受限启动恢复。当前能力请读 07 和 08，不要将本文的未实现项当成当前结论。

先把五种「执行」分开

  1. Session 是会话数据/执行身份；子 agent 也通常有一个 child Session，不等于新 OS 进程。
  2. Effect Fiber 是 JS/Effect 运行时中可组合、可中断的异步执行单位，不自带 PID；Effect.forkIn 不等于 child_process.fork。
  3. Worker 是 TUI 与服务运行时代码之间的线程/独立 JS isolate 边界；不是每个 agent 都创建 Worker。
  4. Bash/shell tool 执行命令时才创建真实 shell 子进程，并可能再有进程组/后代进程。
  5. PTY 是带伪终端的交互式 OS 进程，提供输入、resize、持续输出、attach；不是 agent loop，也不是普通 stdout pipe shell tool。

最容易误读：detached: true 在这里主要服务于 POSIX 进程组管理。工具仍等待退出/结果，不能据此说它已经「模型侧后台返回」。同样，输出通过 Fiber 流式读取，也不代表工具已经返回。

还要区分 shell 自己的后台命令：& 可以启动系统后台进程，但不自动生成 OpenCode 管理的 job ID、观察/取消工具或完成通知。它能否继续存活，要看管道是否仍打开、终端与进程组关系、宿主资源清理等条件。因此本文的“后台 bash 尚未接入”指受管理的模型工具协议，不是说 bash 工具不能运行，也不是说操作系统不支持后台进程。

7. 新 CLI daemon 才是另一个真实宿主进程

V2 相关的新 packages/cli（命令名 lildax）还有另一种“后台”：daemon 服务进程。它与 task 的后台 Fiber 完全不同。

B · daemon.ts:110 通过 spawn(process.execPath, [..., 'serve', '--register'], { detached: true, stdio: 'ignore' }).unref() 启动独立 OS 进程，再用健康/版本检查连接。这里确实多了一个 PID；不是为每个 Session 或子 agent 启一个 daemon。根目录的 bun dev 并不直接走这个新 CLI，见 06。

这是执行层次图，Worker 与 daemon 是不同入口形态，不能理解为所有启动方式都会同时创建两者。多个会话共享宿主并不等于共享对话历史；独立历史也不等于文件系统隔离。
