# 08 · 问答与排查手册：从现象找到负责的那层

本章用于查阅，正文中的概念在前三个版本篇和工具篇有完整代码。A=v1.2.24，B=最终 V1 1.18.35，N=本次固定的 V2 2.2.0。不要把这里的答案无限推广到未来版本；遇到变化先固定提交，再追实际调用链。

## 一、身份和数据

### 1. Agent、Session、模型、执行者到底谁是谁？

Agent 是提示词、模型偏好、权限、步数等策略身份；Session 是对话与历史身份；模型是被调用的推理服务；执行者是此刻推进会话的 loop/Fiber。选择一个 agent 不会自动派生 OS 进程，Session 创建成功也不表示已经请求模型。最小检查法是分别找到配置定义、会话表记录和活动运行映射，看它们是否真的指同一类对象。详见 01、02、03。

### 2. 为什么一个用户问题有多个 assistant、工具和步骤？

模型要先发工具调用、读结果，再决定是否继续。外层 loop/runner 负责把这些调用连接成任务；一个 assistant 不是永远覆盖更新的单一文本框。N 还要区分逻辑 step 和失败的 attempt。内部标题/压缩请求不应直接算成用户业务步骤，工具数量也不等于模型请求数量。

### 3. Session 的 parentID 与消息的 parentID 是一回事吗？

不是。会话 parentID 建父子会话关系；A/B assistant 的 parentID 指回应的 user message。另有工具调用的 provider call ID、本地 part ID、Job ID、shellID、PID。排查串结果时先画身份账本，避免把 child Session ID 当成可以杀进程的 PID。

### 4. 有 SQLite，是不是进程重启就能接着所有工作？

数据库保存了什么，决定能恢复什么。A 已保存消息但没有保存活跃 callbacks；B BackgroundJob 是进程内执行；N 增加 claim、恢复预算和通知 marker，但也没有序列化一个活着的 Fiber。恢复原始事件、读取投影、续接会话、补通知、保留 OS 进程是五种不同能力。

### 5. 原始事件日志为空，为什么消息和 inbox 还在？

N 的 Bus.persist 默认 false。projector、sequence 和 commit hook 仍在事务中更新查询状态，原始 payload 是否额外保留是另一项选择。先确认宿主配置，再判断日志为空是否异常；不要拿 EventTable 为空去推出“所有消息仅在内存”。实时 delta 也不是原始持久日志的代名词。

### 6. 为什么 UI 曾显示的最后几个字，重启后可能没有？

看该版本如何处理 delta。A 的部分流式增量先发给观察者，完整 part 在边界再保存；当前服务的实时传输、投影更新和日志保留也各有边界。看到文本出现在屏幕，只能证明某个连接曾收到它，不自动证明它已经成为完整、可回放的持久消息。

## 二、输入与并发

### 7. prompt 返回成功，是否代表模型完成？

不一定。A/B 同步 prompt 常等 loop 结果，但另有 noReply、异步 HTTP 路径。N prompt 主要返回 admission 收据，执行随后由 wake/coordinator 推进。请从接口返回类型判断等待点，不能只凭函数名。等待 admission、等待当前执行 idle、等待某个业务结果不是同一个 API 语义。

### 8. 两个人同时发给同一 Session，会不会有两个模型同时改历史？

正常本进程路径有防重入协调。A 用活动 controller/callbacks，B 用 Runner，N 用 process-global coordinator。后来的输入与执行等待者如何合并，要按版本理解。这个保证限定于相应宿主协调范围，不等于两个独立机器随便共享 SQLite 也安全。

### 9. wake 和 resume 为什么不合并成一个函数？

因为意图不同。wake 是“新工作到了”的提示，可以合并；没有可交付输入就不必强行请求模型。resume 是显式继续，空闲时可 forced 推进，忙时加入已有执行等待。恢复模糊历史时，这个差别尤其重要，不能让一次随意门铃就无条件重做旧副作用。

### 10. queue 与 steer 会打断正在生成的模型流吗？

输入 admission 不等于原地编辑当前请求。N 通常在安全 step 边界交付 steer，queue 等当前工作将 idle 后取一项。真正的 interrupt 是另一操作。正在进行的请求已经拿到一个消息快照，后来输入要进入后续请求才可能产生影响。

### 11. 同输入 ID 再发一次不同文本，为什么没改成功？

N 的同 Session、同 user/synthetic 类型采用 first admission wins。幂等 ID 表示“同一次发送的重试”，不表示“请覆盖之前文本”。跨 Session 或类型的身份复用则会冲突。要表达新意图，使用新 ID；改 pending 正文可取消旧项并重提，不要把 delivery PATCH 当成文本编辑器。

### 12. 我取消 pending 输入时，怎么模型好像已经看到它了？

取消和交付可能竞争。已经交付的内容不再是 pending 工作，界面点击发生的时间不等于服务器事务提交时间。应处理接口反馈并查询当前 inbox/消息状态；若旧输入已进入历史，需要用后续 steer 明确修正，而不是假设它被追溯抹除。

### 13. 为什么一个 HTTP 等待者断开，不该把整段工作杀了？

连接只是观察者或等待者，owner 是会话执行。N 的 resume joiners 共享 done 结果，但等待者自己的取消不应夺走 owner 的生命周期。否则一个网页刷新就可能中断其他客户端依赖的任务。工具前台等待的取消传播则另有明确设计，不要混成“所有 await 取消都不影响工作”。

## 三、工具、权限与子 agent

### 14. 模型写了个工具调用，是 processor 还是 SDK 真正执行？

A/B 默认 SDK 路径通过注册的 execute 回调调用工具，processor 主要消费事件、保存状态；N 的 step 编排显式执行工具 runtime。看 code branch 中是否真的调用 handler，不要把“记录 tool-call”当成“已经执行副作用”。第 01、02、03、04 章分别给出了真实片段。

### 15. 工具目录里没出现，是权限拒绝还是根本没注册？

可能是不同阶段的问题：插件没有贡献，贡献被过滤，模型目录选择了另一种能力集合，或者 schema/宿主条件不满足。即使目录可见，执行时也还要真正授权。先查默认插件与运行中的快照，再查调用者身份、权限匹配和目标资源，不要仅在 UI 的工具名列表里猜原因。

### 16. explore 是不是安全的只读沙箱？

名字与提示词不能证明沙箱。必须看 agent 权限、Session 限制、工具自身授权和底层宿主能力。A/B explore 默认可用 bash 等能力，shell 也具有宿主用户授权的实际进程能力。N 的权限机制同样不是自动的操作系统隔离；可信插件尤其不能按不可信模型文本来理解。

### 17. child 会复制父会话全部聊天吗？

新子会话通常是 fresh history，父模型应在 prompt 里交接相关内容。Location、Session 元数据、权限与模型的继承又是另一层，不能由“不复制历史”推出“文件系统完全隔离”。续接同一 child ID 则会使用那段子历史，而不是每次清空。

### 18. 为什么不允许拿任意 Session ID 作为 subagent 继续？

因为这条工具链有父子关系与调用者权限。N 会检查 existing.parentID 是否属于当前父 Session，避免任意借用别人的会话身份。这个工具不是一个无限权限的通用 Session 管理接口。想跨应用操作另一会话，需要对应 API 和授权，而不是伪装成 child 续接。

### 19. 子模型怎么选？可以每次偷偷换一个便宜模型吗？

看版本的模型选择顺序。N 新 child 以显式覆盖、agent 配置、父会话模型为优先级；续接还有保留旧子模型和切 agent 的条件。工具提示对“只在用户指定时覆盖”有约束，但描述不是代码级禁止任意可用模型的全部安全边界。审查时要分别看提示、schema、可用目录与执行校验。

### 20. 子 agent 可以无限再派孙 agent 吗？

不能仅凭有 subagent 工具就这么推断。最终 V1 和 N 都有深度及权限约束，配置位置和调用身份要按版本读。默认一层与“用户配置可放宽深度”也不同；放宽深度不自动越过 task/subagent 权限。递归任务还可能放大模型费用和文件竞争，应按真实需要设计。

### 21. V1 已有后台 task，为什么还要 V2 Job？

V1 的实现已经解决父工具先返回、子工作继续和完成回注。V2 进一步统一等待/前后台转换、global 生命周期、通知身份与确认、KV recovery、子会话启动恢复等。改进重点是生命周期和可解释的故障处理，不是把同一个功能改名就算新发明。详细比较在 05，动机在 06。

### 22. 取消父 Session，一定会杀全部后台 child 吗？

不能跨版本这么说。B 有明确的后代后台任务遍历取消；N 的前台等待有 interrupt 传播，后台工作有独立 Job/Session 生命周期，普通 parent interrupt 不应直接套旧递归规则。请按第 04 章把活动父执行、前台 tool scope、后台 job 和 child owner 分开追。

## 四、后台、进程和恢复

### 23. `await`、Fiber、Worker 和后台进程各代表什么？

await 是调用者等待异步结果；Fiber 是 Effect 活动计算；Worker 是独立 JS 执行环境；OS process 有真正 PID。后台则描述是否解除前台等待和怎样通知结果。它们是不同轴：同进程的子会话能后台运行，一个 detached OS shell 也可能仍让工具前台等待。

### 24. 有 `detached:true` 就等于工具支持 background 吗？

不是。detached 在这些命令路径中常服务于进程组与清理；工具可能仍等退出。N 的 background:true 则明确返回 running 身份并建立通知、输出和作业管理。只有 shell 里手写 `&`，不等于得到了这套协议。

### 25. Job 的 wait timeout 会自动杀命令吗？

不要默认如此。等候超时与命令运行超时分属不同层：前者可以只让等待者拿到 timedOut，后者才由命令资源层执行终止。检查具体 wait/block、Shell timeout 和取消参数。把它们混成一个 timeout，常会出现“接口超时了，命令怎么还在跑”的误判。

### 26. 后台测试怎么保证结果不会丢，是否恰好一次？

当前可恢复 Job 有持久通知 ID、终态/恢复信息与确认机制，完成后 synthetic admission，再确认 marker。它减少“完成了但没通知”的丢失窗口，并可利用输入身份处理重试。但外部副作用、provider 是否接受请求等仍可能模糊；通知去重不等于整个业务 exactly-once。

### 27. shell 后台模式默认永不结束吗？

后台通常默认不设命令超时，但进程仍可自行退出、被取消、因服务/宿主失效而终止，或输出错误。没有默认 timeout 不是永生协议。具体 shellID 的状态、输出文件、Job 结果与恢复通知要一起看，不能拿 PID 存在证明测试通过。

### 28. 服务重启以后，后台 shell、child 和 PTY 都怎么了？

它们有三条不同机制。shell recovery 主要补取消/已有终态通知，不盲目重跑命令；child 可在身份和预算检查后 resume；PersistentPty 的独立 daemon 支持受控服务交接，普通 PTY 仍按 scope 管理。受控替换、进程崩溃、daemon 死亡和整机重启的保证不能混为一谈。

### 29. 为什么恢复还要预算？有数据库就一直恢复不好吗？

同一个坏输入、损坏状态或不兼容工具可能让服务每次启动都崩溃。持久恢复计数让系统能在跨进程尝试后明确失败，避免永远循环。预算也不是 exactly-once 协议；它限制尝试次数，不证明每次失败前什么都没做。

### 30. claim 是不是分布式锁？

不是。当前协调仍在单进程 Map；claim 表达一个尚未终结的执行忙碌期，服务受控恢复要确认旧 owner 已死亡。跨节点租约、fencing、共享状态一致性需要另外的完整协议。数据库能保存 owner 相关信息，也不能单凭字段名称证明分布式执行已完成。

## 五、模型、压缩和工程收益

### 31. 为什么要有 step 和 attempt，不能都叫一轮吗？

一次逻辑模型步骤可能经历可重试失败，也可能已有部分输出需要后续 continuation。step 记录模型可见的逻辑跨度，attempt 描述尝试；整个用户任务又可能包含多个 step。把它们都叫“轮”，很容易把费用、重试次数和历史边界算错。N 的仓库约定明确保留这些层次。

### 32. 重试一定从头发送相同内容吗？

不一定。N 会根据是否已有可持久输出、错误种类和策略决定 retry、continue 或失败。工具副作用更不能跟着模型错误一概重放。当前文本 RequestExecutor 默认 executeOnce，Session step 层拥有重试策略；不要继续把旧实现中固定底层 HTTP 重试次数套进新版本。

### 33. 压缩是不是删除数据库里的全部旧聊天？

压缩首先改变后续模型请求如何选择和表示历史，可能写摘要/checkpoint、保留近期内容或标记可裁剪工具输出；它不等于所有存储记录被直接抹去。不同版本的 prune、compaction、revert、archive 又是不同操作。查看真实历史查询和模型 lowering，才能知道模型到底看到了哪一段。

### 34. instructions 文件变化，会不会改掉模型过去见过的内容？

已发出的请求不会倒流。N 的 InstructionState 保存稳定基线、来源 hash 与后续变化，必要时将变化作为按顺序的内容进入后续请求；压缩/移动等还有相应更新边界。当前观察失败与确认删除也不同：不能因为暂时读不到就假装策略已撤销。

### 35. V2 肯定更快、更省 token 吗？

只能逐项证明机制：例如事件编码共享、连接复用机会、稳定 cache 前缀、活动历史压缩。整体收益受模型、provider 缓存、工具耗时、重试、数据库与 UI 负载共同影响；没有同任务对照测量就不能给百分比或保证。新增状态与恢复检查也会增加成本，见 06 的证据分级。

### 36. 跨运行时与 SDK，是否意味着 workerd 也能执行本机 bash？

不意味着。宿主 profile 可替换数据库、进程和文件系统能力；缺少本地执行平面的 workerd 会明确拒绝不支持的操作。能复用 Session 语义与 HTTP 入口，不等于所有原生工具在每个环境都功能等价。还需要相应 sandbox/远程能力接入。

### 37. 插件有类型，为什么仍然可能破坏系统？

类型约束调用契约，Scope 管理注册与资源生命周期；两者不自动把插件变成不可信沙箱。插件可以访问宿主授予的能力，也可能产生外部副作用。transform 的同步可重放要求、注册顺序、snapshot 使用与卸载清理，都需要作者遵守。typed hook 不能替代授权设计。

### 38. 看到一个配置项或 TODO，能否直接判断功能是否实现？

不能。要追三件事：是否有实现、是否注册到实际入口、是否被默认工作流调用。反过来，旧 TODO 也可能落后于代码；V2 推广后工具名、目录和默认入口变化很大。本书固定 SHA，就是为了避免以另一个版本的注释裁定当前实现。

## 六、用一套排查流程回答新问题

### 39. 一个新问题来了，我应该先搜什么？

先把问题改写成可观察事实：“某 Session 的输入已 admission 但没有交付”“某工具返回 running 后没有 completion”“某个 shellID 已退出但父模型仍没读到结果”。然后依次查身份、边界、所有权、提交与通知，不要一开始就在全仓搜 agent 这个泛词。

实用的只读命令是固定提交查看，而非不断切换整个工作目录：

```bash
git show <完整提交SHA>:<仓库相对路径>
git grep -n '<实际符号名>' <完整提交SHA> -- packages/core packages/server packages/protocol
git diff <旧SHA> <新SHA> -- <相关源码目录>
```

尖括号是你需要替换的参数。源码 ZIP 中也提供被本书实际引用的完整文件及行号阅读页，可以先沿片段跳回完整上下文，再搜调用者与实现者。

### 40. 什么时候我才算真正读懂一个机制？

当你能在不依赖界面动画的情况下，画出输入、关键状态、执行所有者、保存结果与失败分支；还能解释一个并发请求、一次取消和一次崩溃分别改变哪项状态。若只能复述“这里用 Effect、这里有 Event、那里开了 Fiber”，还没回答它们为何存在。请用第 07 章的六个场景反复检验，再回到真实源码找自己推演中缺失的那条边。
